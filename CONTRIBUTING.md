# Contributing to HealSync

Thanks for contributing! This document defines how the team works together on
this repository.

## Ground rules

- Follow the [development philosophy](README.md#development-philosophy):
  modular monolith, type safety, services, and documentation.
- Do not introduce infrastructure (services, queues, caches, new frameworks)
  without a documented requirement.
- Keep changes focused. Small, reviewable pull requests are preferred.

## Branch naming

Branches are created from `main` using a conventional prefix:

```
feature/<short-description>   # new functionality
fix/<short-description>       # bug fixes
refactor/<short-description>  # restructuring without behavior change
docs/<short-description>      # documentation only
chore/<short-description>     # tooling, dependencies, maintenance
test/<short-description>      # test-only changes
```

Examples: `feature/patient-feedback-form`, `fix/session-expiry`, `docs/api`.

## Workflow

```
feature branch
      ↓
Pull Request
      ↓
review
      ↓
CI (lint, typecheck, format, tests)
      ↓
merge into main
```

1. Create a branch from `main`.
2. Make your changes; commit often with meaningful messages.
3. Push the branch and open a pull request against `main`.
4. Ensure CI passes (see below).
5. Request review; address feedback; get approval; merge.

## Commit expectations

- Write clear, imperative commit messages describing **what** and **why**.
- Keep related changes in a single commit; split unrelated changes.
- Never commit secrets, `.env` files, build output, or generated files.
- Do not commit the generated Prisma client in `src/generated/` — it is
  regenerated by `pnpm prisma generate` (already gitignored).

## Code formatting

- **Prettier** is the single source of formatting truth. Run it before
  committing:
  ```bash
  pnpm format
  pnpm format:check
  ```
- **ESLint** must pass:
  ```bash
  pnpm lint
  ```
- **TypeScript strict** must pass:
  ```bash
  pnpm typecheck
  ```

## Testing requirements

- Run the unit test suite before pushing:
  ```bash
  pnpm test
  ```
- Add tests with new behavior: unit tests for services/utilities (Vitest),
  e2e tests for user-visible flows (Playwright):
  ```bash
  pnpm test:e2e
  ```
- Do not break the existing smoke tests.

## Pull request expectations

- Title follows conventional prefixes (`feat:`, `fix:`, `docs:`, ...).
- Description summarizes the change, why it is needed, and any trade-offs.
- Mention relevant docs (`docs/*.md`) that need updating.
- CI must be green before merge.
- Link related issues if tracked in the project board.

## Review expectations

- Reviewers check: correctness, security (see `docs/SECURITY.md`), type
  safety, adherence to architecture conventions, test coverage, and
  documentation updates.
- Be respectful and constructive. Focus on the code, not the author.
- Approve only when concerns are resolved.

## Definition of ready

A change is ready to merge when:

- [ ] `pnpm lint` passes
- [ ] `pnpm typecheck` passes
- [ ] `pnpm format:check` passes
- [ ] `pnpm test` passes
- [ ] relevant e2e tests pass
- [ ] no secrets or generated files committed
- [ ] docs updated if behavior/conventions changed
